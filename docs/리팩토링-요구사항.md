# 리팩토링 요구사항 — 머신으로 기록하기

- 작성일: 2026-11-13 · 상태: **확정 · 구현 완료** (스키마 v9)
- 확정된 명세는 [SETTING.MD §15](../SETTING.MD)에 있다. 이 문서는 계기와 결정 기록만 남긴다.
- 결정 방식: 사용자가 Q-01에서 **B**를 고르고, 나머지 질문과 구현 전체를 위임했다("B로 진행하고 … 전체 리팩토링 진행", "내 승인 받지 말고 다 진행"). 위임된 질문은 문서에 적어 둔 ★ 추천안으로 정했다.

## 1. 계기

> 어제 안 쓰던 머신을 쓰려고 종목 추가를 했는데 머신 선택하니까 이름, 운동 부위 같은 것을 선택하라고 나오더라. 머신은 이미 이름이 있고 운동 부위도 정해져서 나오는 게 많은데 이걸 손으로 쓰려니까 귀찮고 불편한 경험이었다. (사용자, 2026-11-13)

DB에 남은 그날의 흐름(KST, 기록상 날짜는 11월 11일):

| 시각 | 일어난 일 |
|---|---|
| 18:47:16 | 머신 `해머 MTS 로우`(Hammer Strength · MTS Iso-Lateral Row)를 내 머신에 담음 |
| 18:47:40 | 종목 `해머 mts 로우` 생성. 기본 타겟 `광배근`, 계열 `로우` |
| 18:47:53–18:51:47 | 그 종목으로 3세트 |
| 19:13:14 | 머신 `라이프 듀얼 어저스터블 풀리 (스태빌라이제이션)`를 내 머신에 담음. 연결된 종목 없음 |

원인: 머신이 **종목**에 붙어 있어서(종목 하나에 머신 0~1대) 새 머신을 기록에 남기려면 새 종목을 만들어야 했고, 종목 폼은 머신을 골라도 `machine_id`만 채웠다. 앱은 머신 1,735대 전부의 한글 이름과 1,424대의 참고 타겟을 이미 갖고 있었다.

## 2. 결정 기록

| 질문 | 결정 | 정한 사람 |
|---|---|---|
| Q-01 새 머신을 만났을 때의 흐름 | **B. 종목에 머신을 붙인다** — 종목은 동작 하나, 머신은 세트마다 남는다 (과제 인터뷰 I-08·REQ-F-16과 같은 구조) | 사용자 |
| Q-02 같은 종목을 다른 머신에서 하면 | PR과 지난 기록을 **머신별로 따로** 센다. 분석 그래프는 종목 기준 그대로 | 위임(★) |
| Q-03 다목적 장비(케이블·스미스·랙·벤치) | 기록에 남긴다. 19:13의 의도는 확인하지 못했다 — 어느 쪽이든 이제 케이블 컬 카드의 머신 칩으로 남길 수 있다 | 위임(★) |
| Q-04 처음 쓰는 머신을 먼저 골랐을 때 | 앱이 종목을 추천하고 사용자가 고른다. 맞는 것이 없으면 머신 이름·참고 타겟이 채워진 새 종목 폼 | 위임(★) |
| Q-05 머신 선택을 얼마나 기억하나 | 같은 종목을 다음에 열면 지난번에 쓴 머신이 선택돼 있다 | 위임(★) |
| Q-06 이미 만든 `해머 mts 로우`(3세트) | 내장 `아이소 래터럴 로우`로 합치고 3세트에 머신을 붙인다. **합칠 종목은 사용자가 지정하지 않아 내가 골랐다** — 머신 모델명이 Iso-Lateral Row이고 그 종목의 별칭이 "해머스트렝스 로우"라서다. 되돌릴 수 있다(SETTING §15.6) | 위임(★) |
| Q-07 고치는 순서 | 자동 채움만 먼저 내보내는 추천안 대신 **한 번에** 반영 | 사용자 |
| Q-08 같이 넣을 것 | 이번에는 넣지 않는다 (신체 기록, 친구 공개 등급, 백업 주기) | 위임(★) |
| Q-09 다 됐다고 볼 기준 | 안 쓰던 머신으로 첫 세트를 저장할 때까지 키보드 입력은 머신 검색어뿐이다 | 위임(★) |

## 3. 요구사항과 충족 여부

| ID | 요구 문장 | 우선순위 | 충족 | 확인한 곳 |
|---|---|---|---|---|
| R-01 | 시스템은 머신을 고른 뒤 새 종목을 만들 때 이름 칸을 머신의 한글 이름으로 채워야 한다. | Must | 예 | e2e D1 |
| R-02 | 시스템은 그 머신에 참고 타겟이 있으면 기본 타겟 칸을 그 값으로 채워야 한다. | Must | 예 | e2e D1 |
| R-03 | 시스템은 사용자가 이미 입력한 이름을 자동 채움으로 덮어쓰지 않아야 한다. | Must | 예 | 검색어가 있으면 그것이 이름이 된다 — 코드로만 확인 |
| R-04 | 시스템은 자동으로 채운 이름·타겟을 저장 전에 고칠 수 있게 해야 한다. | Must | 예 | e2e D2 |
| R-05 | 시스템은 참고 타겟이 없는 머신이면 이름만 채우고 타겟은 사용자가 고르게 해야 한다. | Should | 예 | 폼 검증("기본 타겟 부위를 선택하세요") — 코드로만 확인 |
| R-06 | 시스템은 머신을 직접 추가할 때 참고 타겟도 고를 수 있게 해야 한다. | Could | 예 | 직접 추가 폼 — 코드로만 확인 |
| R-07 | 시스템은 이 변경으로 기존 세트 수와 총볼륨을 바꾸지 않아야 한다. | Must | 예 | 마이그레이션 사전 실행, 옛/새 응답 대조 |
| R-08 | 시스템은 세트마다 그 세트를 수행한 머신을 0~1대 저장해야 한다. | Must | 예 | pytest `test_set_machine`, e2e A3·B4 |
| R-09 | 시스템은 종목을 열 때 사용자가 그 종목에서 마지막으로 쓴 머신을 미리 선택해야 한다. | Must | 예 | pytest, e2e F1 |
| R-10 | 시스템은 PR 여부를 같은 종목·같은 머신의 이전 기록과 비교해 판정해야 한다. | Must | 예 | pytest `test_pr_flags_are_scoped_per_machine`, e2e B4 |
| R-11 | 시스템은 지난 기록을 카드의 머신으로 한 기록에서 찾아 보여 주어야 한다. | Must | 예 | pytest, e2e A2·B3 |
| R-12 | 시스템은 머신을 먼저 고르면 그 머신으로 할 종목 후보를 제시해야 한다. | Must | 예 | pytest `test_machine_match`, e2e B2 |
| R-13 | 시스템은 사용자가 그 머신으로 기록한 종목이 하나뿐이면 그 종목으로 바로 시작해야 한다(한 가지 동작용 머신). | Should | 예 | e2e A2 |
| R-14 | 시스템은 카드의 머신을 바꿀 때 이미 저장한 같은 종목 세트에도 적용할지 물어야 한다. | Should | 예 | e2e C2·G2 |
| R-15 | 시스템은 오프라인에서 저장한 세트의 머신을 연결 복구 후 그대로 전송해야 한다. | Must | 예 | e2e I1 |

Q-09의 기준: e2e B 단계(처음 쓰는 머신 `뉴텍 토크 하이 로우`)에서 키보드 입력은 검색어 하나였고, 탭은 종목 추가 → 머신 → 추천 종목 → 세트 완료의 네 번이었다.

## 4. 운영 규칙 (구현 중 지킨 것)

- 기존 세트와 총볼륨은 바뀌지 않았다. PR 히스토리도 그대로다(기존 세트는 모두 "머신 없음" 범위).
- API 변경은 `frontend/src/api/types.ts`와 계약 테스트를 함께 고쳤다.
- 세트의 머신은 오프라인 큐에도 실린다. 큐에 남은 옛 항목은 머신 없음으로 저장된다.
- 머신 시드의 기존 브랜드·모델 문자열은 바꾸지 않았다.
- 스키마 변경 전에 스냅샷을 떴고, 검증은 운영 DB가 아니라 사본에서 했다. 운영 서버 재시작은 `scripts/restart-server.ps1`로만 했다.
