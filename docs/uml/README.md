# UML 비교 — LLM 액터 없음(A안) · 있음(B안) · 루틴 조언자까지(C안)

- 작성일: 2026-09-21
- 목적: 팀 주제 회의에서 "LLM을 보조 액터로 넣는 설계"가 왜 더 나은 과제 소재인지, 같은 형식의 다이어그램으로 비교한다. A·B안이 기본 비교이고, C안은 LLM을 "조언자"로 쓰는 확장안이다.
- 근거 문서: `docs/HANDOFF-UML.md` §4(액터·유즈케이스)·§6(UC-02·UC-06 명세), `SETTING.MD` §10.4(머신 아카이브), `backend/app/routers/catalog.py`(A안 시퀀스의 실제 API).

## B안을 고를 때의 근거

1. 대체 흐름이 억지로 만들어지지 않는다. LLM은 틀릴 수 있는 액터라 실패 분기가 자연히 생기고, 그 해법이 "사람이 확인한 뒤 등록"이라는 설계 결정으로 이어진다.
2. «extend»를 교과서적으로 쓸 수 있다. 사진 식별은 내 머신 추가의 선택 경로이고, 확장점이 코드상 실제 분기(검색 결과 0건)와 일치한다.
3. 비기능 요구사항을 숫자로 적을 수 있다. 비용·쿼터·응답 시간·개인정보 제약이 전부 정량이다.
4. 기존 시스템(as-is) 위에 신규 기능(to-be)을 분석·설계하는 구성이라, "이미 만든 걸 역공학했다"는 인상을 피한다.

## 반대 근거와 위험 (회의에서 같이 봐야 할 것)

- UC6은 코드가 없다. 평가자가 구현된 시스템을 기대하면 B안의 핵심이 가상 설계로 보일 수 있다. 대응: 사진 20~30장으로 인식률 측정 스크립트를 돌려 타당성 자료를 붙인다. 아직 돌리지 않았다.
- 채점 기준에서 외부 시스템 액터를 어떻게 보는지 확인되지 않았다. 강의에서 "액터 = 사람"으로 좁게 가르쳤다면 감점 위험이 있다. 대응: 강의 자료에 외부 시스템 액터 예시가 있는지 먼저 확인.
- 분기가 7개면 시퀀스 다이어그램이 커진다. 분량 제한이 있으면 A1·A3·A6 세 개만 alt로 그리고 나머지는 명세 표로 뺀다.
- B안 시퀀스의 엔드포인트와 상태 코드(429/422/503)는 이 문서의 제안이다. 팀이 다르게 정해도 된다.
- 비용·쿼터 숫자는 추정치다. 실제 Claude API 이미지 요금으로 다시 계산해야 한다.
- 마감일과 요구 다이어그램 종류가 아직 미확인이다. 요구 목록에 시퀀스가 없다면 시퀀스 두 장은 설득용으로만 쓰고 제출물에서 뺀다.

## C안 — 루틴 공유 + AI 조언자 루틴 추천

B안의 LLM은 이미지를 구조화 데이터로 바꾸는 도구다. C안에서 LLM은 비로소 앱의 분석 데이터(부위별 볼륨·빈도·PR)와 사용자의 요구사항을 읽고 대화로 루틴 초안을 제안하는 "조언자"가 된다. 초안은 사람이 확인·편집한 뒤에만 저장되고, 저장된 루틴은 친구나 상급자가 "4분할 루틴A" 같은 이름으로 묶어 공유하며, 받은 쪽은 복사본을 저장해 편집하고 그 루틴으로 세션을 시작한다.

### C안이 더 보여 주는 것

1. 데이터 흐름 요구사항이 생긴다. LLM에 무엇을 보내고(집계 숫자, 종목·머신 이름) 무엇을 보내지 않는지(세트 원문, 사용자명, 친구)가 설계 항목이 된다. B안에는 없던 종류의 비기능 요구사항이다.
2. 환각 검증이라는 대체 흐름이 생긴다. 초안에 라이브러리에 없는 종목명이 오면 서버가 대조해 표시하고 사용자가 교체한다. 비결정적 액터의 출력을 시스템이 검증하는 사례다.
3. 클래스 다이어그램에 설계 결정이 들어간다. 공유를 참조가 아니라 복사로 하는 이유(원본 수정이 복사본에 번지지 않음, `origin_routine_id`로 출처만 남김)를 그림으로 설명할 수 있다.
4. 상태 다이어그램 소재가 하나 더 생긴다. `routine_share.status`의 sent → saved / revoked.
5. 루틴으로 세션 시작이 기존 세트 기록(UC2)을 «extend» 하므로 as-is와 to-be가 자연스럽게 이어진다.

### C안의 반대 근거와 위험

- 범위가 크게 는다. to-be 유즈케이스 6개, 신규 테이블 5개, 시퀀스 1장, 클래스 1장이 추가된다. 마감일과 팀 인원을 모르는 상태에서 고르면 얕아질 위험이 가장 크다.
- 대응 선택지: C안을 고르면 사진 식별(UC6)을 "향후 확장"으로 내리고, 깊게 다룰 2개를 "세트 기록 + AI 루틴 추천"으로 바꾸는 편이 "조언자" 서사에 맞다. 둘 다 깊게 하면 분량이 두 배다.
- 추천 품질을 평가할 방법이 없다. 과제 채점에는 필요 없더라도 발표 질문으로 나올 수 있다. "사용자가 저장한 비율"을 지표 후보로 적어 두는 정도가 현실적이다.
- 운동 조언에는 책임 문제가 있다. 부상·통증 관련 요청은 조언을 거절하고 안내만 하는 규칙(B3)을 명세에 넣어야 한다.
- 개인 데이터가 외부 API로 나간다. 집계 숫자만 보내더라도 약관·동의 항목이 필요하고, 이 역시 비기능 요구사항으로 적어야 한다.
- 공유 방식(복사 vs 참조), 비친구 공유(공유 코드) 허용 여부, 채팅 턴 상한은 팀이 정할 일이다. 이 문서는 복사·허용·상한 있음으로 가정했다.
- 유즈케이스 17개는 한 장에 담기 벅차다. 전체판은 참고용이고, 발표에는 루틴 패키지만 펼친 `usecase-C-routine-focus.puml`을 쓴다.

## 렌더링

A안·B안·C안 축약판은 `top to bottom direction`으로 같은 배치를 쓴다. C안 전체판만 17개를 담기 위해 `left to right direction`으로 패키지를 세로로 쌓았다. 주 액터는 위, 유즈케이스는 시스템 경계 안, 보조 액터(AI 비전 서비스)는 경계 밖 오른쪽 아래다. A안의 대체 흐름 2개는 UC5 타원 안에, B안의 대체 흐름 7개는 UC6a 노트에 적었다. 4주 분석 게이트의 상세(ISO 주 기준, 403 코드)는 그림에서 빼고 이 표에만 둔다.

Graphviz 없이 렌더링되도록 유즈케이스 파일에 `!pragma layout smetana`를 넣어 두었다. 한글 글꼴은 Windows의 맑은 고딕을 지정했으므로 다른 OS에서는 각 파일의 `skinparam defaultFontName`을 바꾼다.

```
java -jar plantuml.jar -charset UTF-8 -tpng docs/uml/*.puml
```

VS Code PlantUML 확장(jebbs.plantuml)이나 https://www.plantuml.com/plantuml 에 붙여 넣어도 된다. 서버에 붙여 넣으면 내용이 외부로 나간다는 점은 알고 쓴다.

### 직선(Oblique) 변형

`usecase-C-routine-focus-oblique.puml`은 StarUML의 선 스타일 Oblique처럼 액터→유즈케이스를 한 줄 직선으로 그린 변형이다. 두 가지 제약이 있다.

- smetana 레이아웃은 `skinparam linetype`을 무시하므로 이 파일만 pragma를 빼고 Graphviz dot으로 렌더한다 (레이아웃이 원본과 조금 달라진다).
- PlantUML은 `linetype polyline`(장애물을 피해 꺾이는 직선)까지만 지원한다. 한 줄 직선은 `tools\dot-oblique.bat`가 dot 입력의 `splines=polyline`을 `splines=line`으로 바꿔 만든다. 래퍼 안의 dot.exe·python.exe 경로는 이 PC 기준이므로 다른 PC에서는 고친다.

```
cd docs/uml
java -jar plantuml.jar -charset UTF-8 -graphvizdot tools\dot-oblique.bat -tpng usecase-C-routine-focus-oblique.puml
```

위의 `*.puml` 일괄 명령으로 이 파일을 같이 돌리면 래퍼 없이 polyline으로 렌더되어 직선 PNG가 덮어써지니, 일괄 렌더 뒤에는 이 명령을 따로 한 번 더 실행한다. 직선 스타일은 StarUML과 마찬가지로 선이 패키지·다른 요소를 가로지르므로, 발표용으로는 곡선 원본과 나란히 보고 고른다.
