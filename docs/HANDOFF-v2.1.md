## 1. 게이트는 권한이 아니라 데이터 준비도

"권한 제어의 영역"이라는 표현은 절반만 맞다. 구현 계층은 권한과 같지만(관리자 검사와 같은 의존성 자리에 걸어 URL 직접 호출로 우회 불가), 판정 근거는 역할이 아니라 **그 사용자의 데이터 양**이다. 관리자도 자기 데이터 기준으로 똑같이 잠긴다.

| 항목 | 결정 |
|---|---|
| 훈련 주 | 웜업이 아닌 세트가 하나라도 있는 ISO 주(월요일 시작)의 개수. 달력 경과나 세션 수가 아님. 같은 주 세션 3개 = 1주, 웜업만 한 주 = 0 |
| 열리는 조건 | 훈련 주 ≥ `ADVANCED_MIN_WEEKS = 4` (`backend/app/routers/stats.py`). "4주 이하 잠금"을 글자대로 읽으면 5주부터지만, 4주 이동평균이 성립하는 최소 길이가 4주라 4주에서 연다. 상수 하나로 조정 |
| 잠금 응답 | `403 {detail: {code: "insufficient_data", weeks_of_data, required_weeks}}`. `/api/stats/summary.analytics {ready, weeks_of_data, required_weeks}`가 상태를 미리 알려 대시보드가 잠금 카드(진행 n/4주)를 보여 준다 |
| 잠금 범위 | 새 고급 분석 6종만. 기존 대시보드(볼륨·부위별 분배·PR·종목 진행·계열)는 그대로 |
| 구현 | `backend/app/routers/analytics.py`의 `require_analytics_ready`가 라우터(`/api/stats/advanced/*`) 수준 의존성 |

**배포 직후 실제 상태** (2026-09-10 백업 사본으로 확인): 관리자 계정은 훈련 8주라 즉시 열림. 두 번째 계정(ruby9914)은 기록 0주라 잠김(0/4주). 지인이 가입하면 첫 4주는 잠금 카드만 본다 — 이것이 의도한 바가 맞는지 확인 필요.

## 2. 고급 분석 6종

전부 `/api/stats/advanced/*` 아래, §6.1 원칙대로 사전 집계 없이 조회 시 SQL로 계산한다. 대시보드 하단 "고급 분석" 섹션(`frontend/src/components/dashboard/AdvancedAnalytics.tsx`)에 같은 순서로 카드가 놓인다.

| 카드 | 엔드포인트 | 보여 주는 것 | 정의 · 주의 |
|---|---|---|---|
| 분할 실행 점검 | `frequency?weeks=8` | 부위·근육별 주별 세션 수 히트맵, 완료 주 평균, 방치 부위 | 방치 = 자극한 적 있고 14일 이상 지남(`NEGLECT_DAYS`). 한 번도 안 한 부위는 방치가 아니라 '해당 없음'으로 표에서 뺀다 |
| 볼륨 추세 | `trend?weeks=16` | 주간 볼륨 + 4주 이동평균(점선), ACWR 타일 | ACWR = 그 주 ÷ 직전 4주 평균, 1.5 초과 경고(`ACWR_WARN`). 쉰 주는 0으로 평균에 포함. 진행 중인 주는 판정 제외. 완료 주 4개가 더 필요해 실질적으로 5주째부터 값이 난다 |
| 관여 근육 분배 | `attribution?from&to&include_warmup&indirect_weight` | 근육별 직접 세트 + 간접 세트 스택 바, 세트/볼륨 토글 | §3 규칙. 총볼륨에는 더하지 않는다 |
| rep-max 매트릭스 | `rep-max?exercise_id` | 1~12RM: 정확히 그 횟수의 최고 중량, `≥`는 그 횟수 이상으로 든 최고 중량. Rep PR 피드 | Rep PR = 같은 중량으로 이전 세션보다 많은 횟수. §6.3 그대로(그 중량의 첫 세션은 베이스라인, 세션당 1건). '종목별 진행'의 선택 종목을 따른다 |
| 세트 내 피로 곡선 | `fatigue?exercise_id&from&to` | 세션 안 n번째 워킹 세트의 평균 횟수·1세트 대비 비율, 종목 rep range 분포 | 서수는 세션×종목 안에서 다시 매긴다(`set_index`는 세션 전체 번호). 세션 수가 적으면 해석 보류 |
| 강도 존 분포 | `intensity?exercise_id?&from&to` | <60 / 60-70 / 70-80 / 80-90 / 90+ %e1RM 비율, 평균 강도, 전체 rep range | 강도 = 중량 ÷ **그 시점까지** 그 종목의 최고 e1RM(러닝 최고치). 과거를 지금 실력으로 재평가하지 않으며 100% 초과 없음. 초기 데이터에선 첫 세트가 곧 100%라 과대될 수 있다 |

## 3. 간접 볼륨 규칙 — 메인 볼륨은 그대로, 옆에 붙는 보조 데이터

주동근만 합산하고 협응근은 보조 데이터로 쓰자는 제안을 fractional set counting(Baz-Valle 2021, RP의 "간접 세트")으로 구현했다. 종목마다 **보조 근육** 목록을 두고(스키마 v5 `exercise_secondary_target`), 세트 하나가 간접 후보 근육마다 가중치(기본 0.5, 설정에서 ⅓ 선택)를 받는다.

| 상황 | 직접 | 간접 |
|---|---|---|
| (a) 벤치프레스를 기본 타겟(중부 가슴)대로 기록 | 가슴 1 | 삼두 0.5 · 전면삼각근→어깨 0.5 |
| (b) 같은 벤치를 타겟 '삼두'로 바꿔 기록 | 삼두 1 | 가슴(기본 타겟) 0.5 · 어깨 0.5 — 삼두는 간접이 되지 않음 |
| (c) 타겟 '상부 가슴'(세부)으로 기록 | 가슴 1 | 삼두 0.5 · 어깨 0.5 — 가슴은 같은 근육이라 간접 0 |

후보 = 보조 근육 ∪ 종목 기본 타겟, 단 세트 타겟과 같은 근육(level 2)이면 제외, 근육 단위 중복 없음(`set_indirect` VIEW). 세 규칙 모두 테스트로 고정했고, 직접 세트 수가 기존 `/stats/muscles`와 정확히 같다는 것과 총볼륨이 변하지 않는다는 것도 계약 테스트로 묶었다.

> **해석 주의 — 실데이터에서 드러난 점.** 2026-09-10 백업 기준 어깨는 직접 14세트인데 간접 후보가 178세트다(프레스의 전면삼각근 + 로우의 후면삼각근이 전부 어깨로 모임). 0.5를 곱해도 어깨 fractional 세트가 직접의 6배가 된다. 규칙대로이긴 하지만, 이 카드의 어깨·삼두·이두 숫자는 "관여했다"는 뜻이지 "그만큼 훈련했다"는 뜻이 아니다. 가중치를 ⅓로 낮추거나 보조 근육 초안을 줄이는 것이 조정 수단이다.

## 5. 배포 — 연구실 PC에서 (PowerShell)

새 의존성은 없다. 기동 시 v4→v5 이행(테이블 생성 + 보조 근육 채움)이 자동으로 돌며 수 초 안에 끝난다. **uvicorn을 직접 띄우지 말고** 예약 작업으로만 재시작할 것(직접 띄우면 포트 바인딩 전에 이행이 먼저 실행된다).

1. 이행 전 스냅샷 — 서버가 켜진 채로 안전하다.

   ```powershell
   cd C:\code\volume_tarning\backend
   uv run python -c "import sqlite3; sqlite3.connect('data/app.db').execute(\"VACUUM INTO 'data/app-pre-v5-20260910.db'\")"
   ```

2. 코드 받기 · 프론트 빌드

   ```powershell
   cd C:\code\volume_tarning
   git pull
   cd frontend; npm run build; cd ..
   ```

3. 재시작 (관리자 PowerShell)

   ```powershell
   schtasks /End /TN VolumeApp-StartServer
   schtasks /Run /TN VolumeApp-StartServer
   ```

4. 확인 — 기동 로그에 `migration: secondary targets seeded: 267 exercises`가 한 줄 찍히고, 로그인 후 대시보드 하단에 고급 분석 카드 6종이 보이면 끝. 다시 재시작해도 그 줄은 다시 나오지 않는다(한 번만 채움).

   ```powershell
   curl http://127.0.0.1:8000/health
   ```

## 6. 검토가 필요한 것 (사용자 몫)

보조 근육 391종 초안은 `backend/app/seed_data/secondary.py`. 267종에 보조 근육이 있고(1개 122 · 2개 126 · 3개 19), 124종은 고립 종목으로 비어 있다. 초안 작성 시 판단이 갈릴 수 있었던 지점:

- 스쿼트·레그프레스는 둔근만 부여, 내전근은 넣지 않음(보수적 선택). 로우바·세이프티바·제르처 스쿼트에만 척추기립근 추가.
- 풀오버·스트레이트 암 풀다운: 광배 기본이면 가슴+삼두, 가슴 기본이면 광배+삼두 — 가슴 0.5는 과하다고 볼 수 있음.
- 런지 계열: 대퇴사두 기본은 둔근만, 둔근 기본(워킹·리버스)은 대퇴사두+햄스트링으로 비대칭 처리.
- 컬 계열: 일반 컬→전완, 해머 컬→완요골근, 리버스 컬→상완근, 조트만 컬→이두.
- 리어델트 플라이는 펙덱과 대칭으로 비움, 페이스풀·풀어파트만 중부 승모.
- 롤아웃에 고관절굴곡근+광배, 사이드 밴드에 요방형근, 데드버그에 고관절굴곡근 — 모두 이견 가능.
- 역도 계열(클린·스내치·하이 풀)은 3개 상한 때문에 척추기립근을 빼고 대퇴사두/햄스트링/상부 승모 선택.

> **중요한 운영 규칙.** 이행이 끝난 DB는 데이터 파일을 고쳐도 반영되지 않는다(관리자가 앱에서 비운 값을 재기동이 되살리지 않도록 한 번만 채우는 설계). 배포 **전에** 파일을 고치면 그 값이 들어가고, 배포 **후에는** 종목 화면에서 관리자로 수정해야 한다. 검토를 배포 전에 할지, 일단 배포하고 앱에서 고칠지 결정 필요.

실제 기록이 있는 종목 중 보조 근육이 비어 있는 것: 사이드 레터럴 레이즈, 인클라인 덤벨 플라이, 케이블 푸시다운, 원암 케이블 푸시다운, 케이블 오버헤드 트라이셉스 익스텐션(모두 고립 종목이라 의도된 비움), 그리고 커스텀 **케이블 트라이셉스 프레스**(초안 대상이 아니라 비어 있음 — 필요하면 앱에서 추가).

## 7. 알고 수용한 것 · 미결

- 간접 **볼륨(kg)** 은 세트 수만큼 표준적이지 않다(문헌은 세트 기준). 카드 기본은 세트, 볼륨은 토글.
- 게이트 4주는 통계적 근거라기보다 이동평균 성립 조건. 기록을 지워 4주 미만이 되면 열렸던 카드가 다시 잠긴다.
- RP 랜드마크(MV/MEV/MAV/MRV)와 RPE 입력은 여전히 없다. `workout_set.rpe` 컬럼만 있고 UI가 없다.
- CSV 내보내기에 보조 근육 컬럼은 넣지 않았다(기존 계약 유지). 필요하면 별도 결정.
- 번들 크기 경고(750kB, recharts 포함)는 v2와 동일하며 이번에 늘지 않았다.

변경 파일은 커밋 `b5b7bc4`의 23개. 새 파일: `backend/app/routers/analytics.py`, `backend/app/seed_data/secondary.py`, `backend/tests/test_analytics.py`, `frontend/src/components/charts/TrendLineChart.tsx`, `frontend/src/components/dashboard/AdvancedAnalytics.tsx`.
